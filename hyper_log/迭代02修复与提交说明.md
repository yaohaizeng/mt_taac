## 两条任务的迭代思路

两条 Taiji 作业建立在**同一套代码与数据管线**之上：RankMixer NS、`user_ns_tokens=4`、`item_ns_tokens=2`、`num_queries=2` 等与 baseline 一致；差异刻意收敛为**两类互不混杂的假设**，便于事后归因。

### 共同工程前提（否则迭代无从谈起）

1. **必须以 `code.zip` 解压后的 `train.py` 为准**  
   平台上模板自带的 `train.py` 往往落后于本地迭代；若直接执行模板副本，会出现 **`unrecognized arguments`**（例如 `--dense_weight_decay`）。因此两条任务的 `run.sh` 都在启动训练前解压 `code.zip`，并把 **`PYTHONPATH`** 指到解压目录（且对未定义变量使用 **`${PYTHONPATH:-}`**，兼容 `set -u`）。

2. **对照的可比性**  
   除「任务 B 单独写的结构/优化器相关超参」外，两条尽量共用 batch、worker、`patience`、`buffer_batches` 等，减少混杂变量。

### 任务一：`taac_baseline_iter02_fix_v2`（正则 / 优化主线）

| 维度 | 思路 |
|------|------|
| **要回答的问题** | 在**不改变默认 HyFormer 深度**（`num_hyformer_blocks` 默认 **2**）的前提下，通过 **Dense 侧权重衰减（AdamW `dense_weight_decay`）** 等方式抑制过拟合，能否稳住验证指标、改善迭代 02 附近出现的「拟合过快 / 泛化变差」类现象。 |
| **损失与优化** | 训练目标仍为 baseline 的 **BCE**；在 **dense 参数**上施加 **`weight_decay=0.01`**（由 `train.py`/`trainer.py` 中的 `--dense_weight_decay` 接入 AdamW），sparse 侧仍用独立 **`sparse_lr`**，与「只改结构」的路径区分开。 |
| **学习率** | **`lr=9e-5`**、**`sparse_lr=0.04`**，与加深网络那条相比略偏高一档：模型容量未放大时，允许稍强的 dense 更新步长；若验证仍抖动，再考虑与任务二交叉微调。 |
| **正则** | **`dropout_rate=0.05`**，作为与任务二（略低 dropout）对称的对照：任务一侧重「不加深网络时的正则强度」，而非靠减深度以外的结构改动。 |

**小结**：任务一是在 **固定容量（2 个 HyFormer block）** 下验证「**BCE + dense 权重衰减 + 既定 dropout/lr**」是否构成可靠的**抗过拟合主线**；工程上对应 `bundle_A_bce/run.sh` → `submit_bundle_iter02_fix`。

### 如何对比两条结果

- **若任务一明显优于任务二**：可能当前数据与训练步数下 **2-block + 较强正则** 已足够，加深带来优化难度或冗余参数，优先考虑沿正则/lr 网格继续搜，而非继续加深。  
- **若任务二明显优于任务一**：提示 **容量** 可能是短板，可在「3 block + 任务二的 lr/dropout 邻域」内细调，或与任务一的 `dense_weight_decay` 做小规模组合试验（注意一次只改一类因素以利于归因）。  
- **若两者接近**：说明瓶颈可能在数据、特征或其它模块（而非单独深度或单独 wd）；下一轮迭代应回到日志与验证曲线，避免在同一窗口堆叠过多超参改动。

## 为什么有时会提示「要你本机跑 submit」？

- **`taac_iter02_overfit_mitigation`（106260）** 那次确实曾 **`--execute` 成功**：说明你当时的运行环境（网络能访问 Taiji API）允许 CLI 完成上传与创建作业。
- 之后在 Cursor **自动化沙箱**里执行同一命令时，多次出现 **`fetch failed`**：这是 **当前会话所在环境的出口网络/TLS 策略不稳定或被拦**，不是 Taiji 禁止脚本提交。
- 因此：**同一套命令在你本机终端通常可以自动提交**；在 IDE 内置环境里则可能失败。能自动提交时我会继续代跑；失败时才会请你本地执行同一命令。

### Model Evaluation 复盘（`best_model`，已由你跑出）

| 训练 Job Name | 评测 AUC |
|---------------|----------|
| **`ns time test`（baseline）** | **0.846668** |
| `taac_baseline_iter03_reg` | 0.84601 |
| `taac_baseline_iter03_depth3` | 0.844648 |

**原因归纳**

1. **相对 baseline 偏离过大**：`ns time test` 等价于 **`lr=1e-4`、`sparse_lr=0.05`、`dropout=0.01`、`dense_weight_decay=0`、`patience=5`、`buffer_batches=20`**（见 `baseline_ns_time_test.md`）。iter03 同时 **`lr 8e-5`、`sparse 0.036`、`dropout 0.06`、`dense_wd 0.02`、`patience 12`**，优化强度显著变弱 + 正则显著变强 → **容量利用不足 / 欠拟合**，线上评测常低于 baseline。
2. **验证曲线≠评测**：曾依据训练验证集「中后期回落」加重正则；但 **评测集与验证划分不一致**，过度压制训练动态反而会伤评测（iter03_reg 已接近但仍落后即为信号）。
3. **深度线**：在已有「强正则 + 低 lr」上叠加 **3-block** 与 **更小 batch**，优化更难，评测降幅更明显。
